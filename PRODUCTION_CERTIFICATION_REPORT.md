## Certification-closure implementation

The release tool now derives state from validated evidence envelopes. Machine
envelopes are generated by type-specific adapters from actual runner outputs;
their unique source roles and SHA-256 hashes are revalidated and their
substantive payload is re-derived when loaded. A correct source hash alone is
not sufficient. The deployment fingerprint covers material runtime, model,
policy, prompt/termbase, OCR, dependency, schema, repair, and corpus inputs.
The certification fingerprint uses deterministic evidence identities that
exclude generated timestamps and packaging paths.

The production doctor now uses the authoritative `ModelPolicy`, verifies OCR
asset content hashes and symlink/path safety, checks exact dependency/runtime
identity, verifies release-manifest and evidence hashes, and reports
`CERTIFICATION_STALE` when the deployment or certification identity no longer
matches. `approved:` string prefixes are not accepted as model approval.

The lightweight local SBOM remains explicitly development-only. Certified
release generation requires a real CycloneDX environment/image SBOM produced
by `cyclonedx-py` in the approved release environment.

The current adapter identity is 2.0. Model evidence now separates the stable
deployment/behavior identity from the experiment-plan identity. Validation and
held-out evidence must cover the complete frozen scenario × format × repeat
matrix; high-risk evidence uses `scenario_id + format` and evaluates every
declared group. A candidate profile describes deployment inputs and need not
pre-claim the release state later derived from its evidence.
